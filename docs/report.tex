\begin{abstract}
This report documents the design, synthesis and testing of a Nios~II soft-core system on the
Altera/Terasic DE2 (Cyclone~II) development board using Quartus~Prime and Qsys (Platform Designer).
Part~A builds a base Nios~II system with on-chip memory, a JTAG UART, an interval timer, parallel
I/O and a system ID peripheral, and extends it with the board's 512~KB SRAM and 8~MB SDRAM,
verified using the Nios~II IDE memory test utility. Part~B extends this system with a custom
combinational instruction, \texttt{count\_leading\_ones}, that counts the number of leading `1'
bits in a 32-bit word in a single cycle. Its design is presented as a Mealy finite state machine,
implemented in Verilog, and integrated into the system as a Nios~II custom instruction slave. Its
performance is measured against an equivalent C software routine, with the hardware instruction
found to be approximately 8$\times$ faster on average.
\end{abstract}

\chapter{Introduction}

This assignment builds familiarity with FPGA (Field Programmable Gate Array) engineering through
the use of \textbf{Qsys}~\cite{qsys} and the \textbf{Nios~II}~\cite{nios_ii} processor.
Nios~II is \textbf{Altera's}~\cite{altera} own 32-bit embedded processor micro-architecture,
designed specifically for synthesis on FPGA. Nios~II is the successor to Altera's first
configurable 16-bit embedded processor, Nios, introduced in 2000. Throughout this assignment we
target the Cyclone~II FPGA on the Altera DE2 board, which we synthesise designs for, bench test
and program over the course of the work.

Nios~II offers the following design parameters:
\begin{itemize}
    \item 32 general-purpose 32-bit registers.
    \item A full 32-bit instruction set, data path, and address space.
    \item A single-instruction 32$\times$32 multiply and divide, producing a 32-bit result.
\end{itemize}

Nios~II's soft-core nature (a soft microprocessor is a microprocessor core wholly implemented
using logic synthesis, and can be targeted at different semiconductor devices containing
programmable logic, e.g. FPGA or CPLD, spanning both high-end and commodity
applications~\cite{soft-microprocessor}) enables hardware engineers to specify and generate a
custom Nios~II core, tailored to their own application requirements.

Qsys (now known as Platform Designer) is a system integration tool for Intel Quartus Prime. It
connects multiple intellectual property (IP) blocks, processors (such as Nios~II), and memory
interfaces using standard interconnects such as Avalon, and can be used to generate the resulting
system as synthesisable HDL.

This assignment is split into three parts. \textbf{Part~A} synthesises a Nios~II processor system
with 20~KB of on-chip memory, a timer, a JTAG UART, 8 parallel I/O pins and a system ID component,
then interfaces the DE2 board's 512~KB SRAM and 8~MB SDRAM to this design. The design is tested
using the memory test programs within the Nios~II IDE, printing name and student ID to the
terminal each time a memory test is run. \textbf{Part~B} continues from Part~A, adding a custom
instruction that counts the number of leading `1' bits in a 32-bit word, together with a C test
program that exercises the instruction. A software routine implementing the same functionality is
also written and benchmarked in C, so that the custom instruction's execution speed can be
compared against an equivalent software implementation. \textbf{Part~C} uses PWM to control the
intensity of LEDR10.

\chapter{Part B - Custom Instruction}

\section{Algorithm Design}

The goal of the custom instruction is to count the number of leading `1' bits in a 32-bit word,
i.e. the length of the run of `1's starting at the most significant bit (MSB) and ending at the
first `0' bit (or at the LSB, if the word is all ones). Before implementing this in Verilog, the
algorithm was designed as a Mealy finite state machine (Harris \& Harris style), treating the
32-bit input word as a serial bit-stream presented MSB-first.

The machine has two states: $S_1$, the \emph{counting} state, and $S_2$, the \emph{done} state.
Starting in $S_1$, every `1' bit received increments a running counter and keeps the machine in
$S_1$; the first `0' bit received transitions the machine to $S_2$ without incrementing the
counter, and the machine then remains in $S_2$ (absorbing any remaining bits with no further
effect) since the leading-ones run is over. Figure~\ref{fig:fsm} shows the resulting state
diagram.

\begin{figure}[H]
    \centering
    \begin{tikzpicture}[shorten >=1pt, node distance=4.2cm, on grid, auto, thick,
            every state/.style={minimum size=1.5cm}]
        \node[state, initial, initial text=] (S1) {$S_1$};
        \node[state, accepting, right=of S1] (S2) {$S_2$};

        \path[->]
            (S1) edge [loop above] node {$1$ / count++} (S1)
            (S1) edge node {$0$ / --}                   (S2)
            (S2) edge [loop above] node {$0,1$ / --}     (S2);
    \end{tikzpicture}
    \caption{Mealy machine for the leading-ones counting algorithm. The input word is streamed
    MSB $\rightarrow$ LSB. $S_1$ (initial state) counts consecutive leading `1' bits; the first
    `0' bit moves the machine to the terminal state $S_2$, after which the count no longer
    changes.}
    \label{fig:fsm}
\end{figure}

Formally, the machine is the 6-tuple $M = (Q, \Sigma, \Gamma, \delta, \omega, q_0)$, where:

\begin{itemize}
    \item $Q = \{S_1, S_2\}$ -- the finite set of states.
    \item $\Sigma = \{0, 1\}$ -- the finite input alphabet (one bit per clock/step).
    \item $\Gamma = \mathbb{Z}^{+}$ -- the output alphabet (the running leading-ones count).
    \item $q_0 = S_1$ -- the initial state.
    \item $\delta: Q \times \Sigma \rightarrow Q$ -- the state transition function, given in
          Table~\ref{tab:fsm-delta}.
    \item $\omega: Q \times \Sigma \rightarrow \Gamma$ -- the Mealy output function: emits
          \texttt{count++} on $\delta(S_1, 1)$, and no output (count held) otherwise.
\end{itemize}

\begin{table}[H]
    \centering
    \caption{State transition function $\delta$}
    \label{tab:fsm-delta}
    \begin{tabular}{lccc}
        \toprule
        Current state & Input & Next state & Output $\omega$ \\
        \midrule
        $S_1$ & 1 & $S_1$ & count++ \\
        $S_1$ & 0 & $S_2$ & -- \\
        $S_2$ & 0 & $S_2$ & -- \\
        $S_2$ & 1 & $S_2$ & -- \\
        \bottomrule
    \end{tabular}
\end{table}

Because the FSM only ever needs to hold a running count and knowledge of whether a `0' bit has
already been seen, it maps directly onto a combinational priority-encoder style circuit rather
than a literal bit-serial shift register: the same result can be produced in a single clock cycle
by evaluating the run of leading ones over the whole 32-bit word at once, halving the search space
at each stage (16/8/4/2/1 bits). This is the structure used for the Verilog implementation in
Section~\ref{sec:custom-instr-hw}.

\section{Software Implementation}

Before implementing the custom hardware instruction, a reference software routine implementing
the same leading-ones-count algorithm was written in C for the Nios~II IDE, so that its speed
could later be compared against the hardware instruction. \texttt{count\_leading\_ones()}
implements the bit-serial algorithm from Figure~\ref{fig:fsm} directly: it walks the word from bit
31 down to bit 0, incrementing a counter for each `1' bit and breaking on the first `0'. A
\texttt{PERFORMANCE\_TEST} mode is included, which repeats the count over
100{,}000 pseudo-varied input words and reports the average execution time per call using the
standard C \texttt{clock()} API.

\begin{lstlisting}[language=C]
#include <stdio.h>
#include <stdint.h>
/* #define PERFORMANCE_TEST */
#define PERFORMANCE_TEST
#ifdef PERFORMANCE_TEST
#include <time.h>
#define PERFORMANCE_TEST_ITERATIONS 100000u
#endif
static const uint32_t word = 0xFA000000;
int count_leading_ones(uint32_t value)
{
	uint32_t leading_ones = 0;
	int i;
	for (i = 31; i >= 0; i--)
	{
		uint32_t bit = (value >> i) & 1;
		if (!bit) {
			break;
		}
		++leading_ones;
	}
	return leading_ones;
}
#ifdef PERFORMANCE_TEST
static void run_performance_test(void)
{
	clock_t start, end;
	clock_t elapsed_ticks;
	uint32_t elapsed_us;      /* total time in microseconds, integer */
	uint32_t avg_x100_us;     /* average per call, in hundredths of a microsecond */
	uint32_t i;
	volatile int result = 0; /* volatile so the compiler can't optimize the loop away */

	printf("Running performance test (%u iterations)...\n",
	       PERFORMANCE_TEST_ITERATIONS);

	start = clock();
	for (i = 0; i < PERFORMANCE_TEST_ITERATIONS; i++)
	{
		/* Vary the input word each iteration so the result can't just
		 * be computed once and cached by the compiler. */
		uint32_t test_word = word ^ i;
		result = count_leading_ones(test_word);
	}
	end = clock();

	elapsed_ticks = end - start;
	/* Convert clock ticks to microseconds using integer math only
	 * (avoids the small-C-library printf %f limitation). */
	elapsed_us = (uint32_t)(((uint64_t) elapsed_ticks * 1000000u) / CLOCKS_PER_SEC);
	/* Average per call, scaled by 100 so we can print two decimal places
	 * without any floating point. */
	avg_x100_us = (uint32_t)(((uint64_t) elapsed_us * 100u) / PERFORMANCE_TEST_ITERATIONS);

	printf("Performance test complete.\n");
	printf("  Total time   : %lu us (%lu ticks)\n",
	       (unsigned long) elapsed_us, (unsigned long) elapsed_ticks);
	printf("  Avg per call : %lu.%02lu us\n",
	       (unsigned long) (avg_x100_us / 100u),
	       (unsigned long) (avg_x100_us % 100u));
	printf("  Last result  : %d\n", result);

	if (elapsed_ticks < 10)
	{
		printf("  Warning: elapsed ticks very low (%lu) - increase\n"
		       "  PERFORMANCE_TEST_ITERATIONS for a more reliable\n"
		       "  measurement; clock() resolution is limited by the\n"
		       "  system timer period.\n", (unsigned long) elapsed_ticks);
	}
}
#endif
int main()
{
	printf("Hello from Nios II!\n");
#ifdef PERFORMANCE_TEST
	run_performance_test();
#else
	{
		uint32_t leading_ones = count_leading_ones(word);
		printf("leading ones %lu\n", (unsigned long) leading_ones);
	}
#endif
	return 0;
}
\end{lstlisting}


\subsection{Software Performance Result}

Running the software routine for 100{,}000 iterations on the Nios~II system gives an average
execution time of 24.63~\textmu s per call:

\begin{lstlisting}
Running performance test (100000 iterations)...
Performance test complete.
  Total time   : 2463000 us (2463 ticks)
  Avg per call : 24.63 us
  Last result  : 5
\end{lstlisting}

Because the loop breaks as soon as the first `0' bit is encountered, this cost is data-dependent:
words with fewer leading ones return faster, while a word of all `1' bits takes the full 32
iterations.

\section{Hardware Custom Instruction}
\label{sec:custom-instr-hw}

The FSM from Figure~\ref{fig:fsm} was re-expressed as a combinational priority-encoder tree
(rather than a literal bit-serial state machine) so that it could be implemented as a Nios~II
\emph{combinational} custom instruction -- one that produces its result within the same clock
cycle it is issued, with no internal state or extra latency. The word is repeatedly halved: first
checking whether the upper 16 bits are all `1', then the upper 8 of whichever half was selected,
and so on down to a single bit, accumulating the count as each stage resolves. This directly
mirrors $\delta(S_1, 1)$ (stay in $S_1$, increment count) versus $\delta(S_1, 0)$ (move to $S_2$,
stop counting) from the FSM, but evaluates all bit positions in parallel instead of serially.

\begin{lstlisting}[language=verilog]
module count_leading_ones (
    // Nios II custom instruction slave interface
    // "ncs_" prefix lets Platform Designer auto-recognize these as the
    // Nios II custom instruction slave interface (clk, clk_en, reset,
    // dataa, result) instead of guessing a generic Avalon-MM slave.
    ncs_clk,
    ncs_clk_en,
    ncs_reset,
    ncs_dataa,
    ncs_result
);

input         ncs_clk;
input         ncs_clk_en;
input         ncs_reset;
input  [31:0] ncs_dataa;
output [31:0] ncs_result;

// Priority tree, halving each stage - pure combinational.

wire msb16_all1 = (ncs_dataa[31:16] == 16'hFFFF);
wire [15:0] next16 = msb16_all1 ? ncs_dataa[15:0] : ncs_dataa[31:16];

wire msb8_all1 = (next16[15:8] == 8'hFF);
wire [7:0] next8 = msb8_all1 ? next16[7:0] : next16[15:8];

wire msb4_all1 = (next8[7:4] == 4'hF);
wire [3:0] next4 = msb4_all1 ? next8[3:0] : next8[7:4];

wire msb2_all1 = (next4[3:2] == 2'b11);
wire [1:0] next2 = msb2_all1 ? next4[1:0] : next4[3:2];

wire msb1_all1 = next2[1];
wire bit0 = msb1_all1 ? next2[0] : 1'b0;

assign ncs_result = (msb16_all1 ? 16 : 0)
                   + (msb8_all1  ? 8  : 0)
                   + (msb4_all1  ? 4  : 0)
                   + (msb2_all1  ? 2  : 0)
                   + (msb1_all1  ? 1  : 0)
                   + (msb1_all1 & bit0 ? 1 : 0);

endmodule
\end{lstlisting}

Once the Verilog above was synthesised, it was imported into Qsys as a Nios~II custom instruction
component (the \texttt{ncs\_*} port prefix lets Platform Designer auto-detect it as a custom
instruction slave rather than a generic Avalon-MM slave) and connected to the Nios~II core's
\texttt{custom\_instruction\_master} interface, as shown in Figure~\ref{fig:ci-slave}
(\texttt{count\_leading\_ones\_0}, opcode~0). This exposes the circuit in software as the GCC
built-in \texttt{\_\_builtin\_custom\_ini(...)} custom instruction call, which the Nios~II compiles
down to a single \texttt{custom} instruction.

\end{lstlisting}

Unlike the software loop, this cost is constant regardless of the input word, since the
combinational priority-encoder tree resolves every bit position in the same clock cycle no matter
how many leading ones are present.

The custom instruction is roughly $24.63 / 3.03 \approx 8.1\times$ faster on average than the
software routine. This is the expected outcome: the software version executes a data-dependent
loop of up to 32 iterations, each costing at least a shift, mask, compare, branch and
increment, whereas the hardware version resolves the whole 32-bit priority-encoder tree
combinationally in a single cycle, with the remaining measured time in both cases dominated by the
fixed overhead of the function/instruction call, loop bookkeeping in the benchmark harness, and
\texttt{clock()} itself.

\textbf{Software routine} - pros: no additional FPGA logic resources are consumed, it is portable
to any Nios~II configuration (or indeed any target) without hardware changes, and it is trivial to
modify or debug. Cons: execution time is both slower and data-dependent (worst-case 32 iterations
for an all-ones word), and it consumes instruction-fetch and data-path bandwidth on the processor
for every iteration of the loop.

\textbf{Hardware custom instruction} - pros: constant, single-cycle latency regardless of input
value, and it frees the processor from executing a software loop at all. Cons: it consumes FPGA
logic resources (comparators and multiplexers for the priority-encoder tree), occupies one of a
limited number of custom instruction opcode slots, requires the Qsys system to be regenerated and
the FPGA reprogrammed whenever it changes, and is tied to this specific Nios~II system rather than
being portable in software alone.

Overall, for a leading-ones count that is executed frequently or on a performance-critical path,
the custom instruction is clearly the better choice, trading a small, fixed amount of FPGA fabric
for an $\sim\!8\times$ speed-up and deterministic timing. For infrequent or non-critical use, the
software routine is preferable, since it avoids consuming custom instruction and logic resources
that could otherwise be used elsewhere in the design.


\chapter{Part C - PWM Module}

For Part~C, PWM is used to gradually vary the intensity of LEDR10 from off to fully on and back to
off, repeating continuously, as required by the assignment brief. Two hardware modules are used
together: \texttt{pwm}, an Avalon-MM slave peripheral that generates the actual PWM waveform from
an 8-bit duty register, and \texttt{ci\_pwm\_controller}, a Nios~II custom instruction that lets
software set the LED brightness using a simple 0-9 level rather than a raw 8-bit duty value.

\section{Design}

The assignment brief suggests two ways to implement the PWM generator: the simplest is to expose
the duty register as a plain Qsys GPIO component and build the counter and comparator as
free-standing logic outside Qsys, wiring the GPIO's parallel output into it by hand at the BDF
level; the more elegant alternative is to package the register, counter and comparator together as
a single custom Avalon-MM slave component inside Qsys. The GPIO route was rejected here because it
splits one logical peripheral across two design domains - a Qsys-managed register and a
hand-wired BDF block - doubling the places a clocking or reset mistake could be introduced, and
because it exposes the raw duty register directly on the Avalon bus with no scope to add
Avalon-native handshaking (e.g.\ the write-strobe re-timing described below) without leaving Qsys
entirely. The single-component approach was chosen instead: it keeps the counter and comparator
under the same reset domain and clock as the register that drives them, lets Qsys's own
address/interrupt allocation manage the peripheral like any other memory-mapped device, and, as
Section~\ref{sec:custom-instr-hw} shows, made it straightforward to later add a second, custom
instruction front-end (\texttt{ci\_pwm\_controller}) onto the same underlying \texttt{pwm} block
without touching its internal register/counter/comparator logic.

The core PWM design - a duty register, an up-counter, and a comparator between them, exactly the
three-part structure suggested in the assignment brief - was originally developed as a standalone
module in a previous assignment. For this assignment it was re-purposed as an Avalon-MM slave so
that it could be instantiated and wired up entirely within Qsys/Platform Designer, rather than as a
free-standing block connected by hand outside the generated system. Figure~\ref{fig:block-diagram}
shows the module's external interface and its internal register structure, and
Figure~\ref{fig:asm-diagram} shows the ASM chart for its controller, covering reset, the
write-strobe path that loads a new duty value, and the two symmetric counting paths that drive
\texttt{pwm\_out} high while the counter is below the duty value and low otherwise.

\section{PWM Peripheral}

Making the module Avalon-MM compliant required more than just adding a register: the port names
(\texttt{reset\_n}, \texttt{write}, \texttt{writedata}) were chosen specifically to match Avalon-MM
naming conventions, so that Qsys Component Editor's "Analyze Synthesis Files" step auto-detects the
clock, reset and Avalon slave interfaces without any manual signal-role assignment. The write path
was also re-timed so that \texttt{pwm\_out} registers from the same next-state values used to
update \texttt{pwm\_counter} and \texttt{duty\_reg}, removing a delta-cycle race that would
otherwise exist between the counter changing and \texttt{pwm\_out} being sampled against it.

\begin{lstlisting}[language=verilog]
module pwm #(
    parameter 			PWM_CLK_DIV             = 194,
    parameter 			PWM_RESOLUTION          = 254,
    parameter [7:0] 	DEFAULT_DUTY_REG  = 8'h02
)(
    input        		clk,
    input        		reset_n,
    input        		write,
    input [31:0]  	writedata,
    output reg   		pwm_out
);
    reg [7:0] duty_reg;
    reg [7:0] pwm_counter;
    reg [7:0] divider;
    // Next-state values computed one cycle ahead, so pwm_out registers
    // from the SAME values used to update pwm_counter/duty_reg. This
    // removes the delta-cycle race with anything sampling pwm_out
    // right after pwm_counter changes.
    reg [7:0] next_counter;
    reg [7:0] next_duty;
    always @(*) begin
        next_duty = write ? writedata[7:0] : duty_reg;
        if (pwm_counter == PWM_RESOLUTION)
            next_counter = 8'd0;
        else if (divider == PWM_CLK_DIV)
            next_counter = pwm_counter + 1'b1;
        else
            next_counter = pwm_counter;
    end
    always @(posedge clk or negedge reset_n) begin
        if (!reset_n) begin
            pwm_counter <= 8'd0;
            divider     <= 8'd0;
            duty_reg    <= DEFAULT_DUTY_REG;
            pwm_out     <= (8'd0 < DEFAULT_DUTY_REG);
        end else begin
            duty_reg    <= next_duty;
            pwm_counter <= next_counter;
            if (pwm_counter == PWM_RESOLUTION) begin
            end else if (divider == PWM_CLK_DIV) begin
                divider <= 8'd0;
            end else begin
                divider <= divider + 1'b1;
            end
            pwm_out <= (next_counter < next_duty);
        end
    end
endmodule
\end{lstlisting}

\section{PWM Level Custom Instruction}

Driving \texttt{pwm} directly from software means every LED brightness change requires computing
and writing an 8-bit duty value, and, since it is a plain Avalon-MM slave, requires the CPU to
issue an ordinary store instruction to its address. To make the application code simpler, a second
custom instruction, \texttt{ci\_pwm\_controller}, was added: it accepts a brightness \emph{level}
from 0-9 on \texttt{ncs\_dataa}, converts it to the corresponding 8-bit duty value, and issues the
Avalon-MM write to \texttt{pwm} itself. Because that write can take a variable number of cycles
(the peripheral's \texttt{avm\_waitrequest} signal is not guaranteed to deassert on the very next
cycle), this cannot be a single-cycle \emph{Combinational} custom instruction like
\texttt{count\_leading\_ones} in Part~B; instead it is registered as an \emph{Extended} custom
instruction, which adds explicit \texttt{ncs\_start}/\texttt{ncs\_done} handshake signals so the
Nios~II core can stall for exactly as many cycles as the instruction needs. Figure~\ref{fig:ci-pwm-asm}
shows the resulting two-state controller: \texttt{IDLE} waits for \texttt{ncs\_start} and then
latches the converted duty value and asserts \texttt{avm\_write}; \texttt{WRITE} holds that write
until \texttt{pwm} deasserts \texttt{avm\_waitrequest}, at which point \texttt{ncs\_done} pulses for
one cycle and control returns to \texttt{IDLE}.

\begin{lstlisting}[language=verilog]
module ci_pwm_controller #(
    parameter [31:0] PWM_BASE_ADDR = 32'h0008_8000
)(
    // Standalone clock/reset ports, NOT used anywhere in the logic below.
    // These exist purely so Platform Designer's Component Editor
    // auto-detects a genuine Clock Input / Reset Input interface (named
    // "clock" / "reset" once analyzed) for avalon_master_0's Associated
    // Clock / Associated Reset dropdowns to point at - a Custom
    // Instruction Slave's internal clk/reset don't count as a valid
    // clock source for that association. At the system level in
    // Qsys/Platform Designer, wire both of these to clocks_sys... same
    // as every other component; it's the same physical clock as ncs_clk,
    // just exposed a second way so the tool's interface bookkeeping is
    // satisfied.
    input              clk,
    input              reset,

    // Nios II Custom Instruction Slave Interface
    input              ncs_clk,
    input              ncs_clk_en,
    input              ncs_reset,
    input              ncs_start,
    input      [31:0]  ncs_dataa,
    output reg [31:0]  ncs_result,
    output reg         ncs_done,
    // Avalon-MM Master Interface
    output reg [31:0]  avm_address,
    output reg         avm_write,
    output reg         avm_read,
    output reg [31:0]  avm_writedata,
    input      [31:0]  avm_readdata,
    input              avm_waitrequest
);

    // Brightness level (0-9) -> 8-bit PWM duty value, spanning 0..254
    // in ~28-count steps. Levels 10-15 clamp to full brightness (254)
    // rather than producing an out-of-range or wrapped value.
    function [7:0] level_to_duty;
        input [3:0] level;
        begin
            case (level)
                4'd0: level_to_duty = 8'd0;
                4'd1: level_to_duty = 8'd28;
                4'd2: level_to_duty = 8'd56;
                4'd3: level_to_duty = 8'd85;
                4'd4: level_to_duty = 8'd113;
                4'd5: level_to_duty = 8'd141;
                4'd6: level_to_duty = 8'd170;
                4'd7: level_to_duty = 8'd198;
                4'd8: level_to_duty = 8'd226;
                default: level_to_duty = 8'd254; // level 9, and 10-15 clamp here too
            endcase
        end
    endfunction

    localparam IDLE  = 1'b0,
               WRITE = 1'b1;

    reg state;

    always @(posedge ncs_clk or posedge ncs_reset) begin
        if (ncs_reset) begin
            state         <= IDLE;
            ncs_done      <= 1'b0;
            ncs_result    <= 32'd0;
            avm_write     <= 1'b0;
            avm_read      <= 1'b0;          // this master never reads
            avm_address   <= PWM_BASE_ADDR; // constant, set once
            avm_writedata <= 32'd0;
        end else if (ncs_clk_en) begin
            case (state)
                IDLE: begin
                    ncs_done <= 1'b0;
                    if (ncs_start) begin
                        avm_writedata <= {24'd0, level_to_duty(ncs_dataa[3:0])};
                        avm_write     <= 1'b1;
                        state         <= WRITE;
                    end
                end

                WRITE: begin
                    if (!avm_waitrequest) begin
                        // Slave accepted the write this cycle
                        avm_write  <= 1'b0;
                        ncs_result <= {24'd0, level_to_duty(ncs_dataa[3:0])};
                        ncs_done   <= 1'b1;
                        state      <= IDLE;
                    end
                    // else: hold avm_write/avm_writedata steady and wait
                end

                default: state <= IDLE;
            endcase
        end
    end

endmodule
\end{lstlisting}

The module above interfaces to the Nios~II core as a Custom Instruction Slave on opcode~1, and
separately drives \texttt{pwm}'s Avalon-MM slave port through its own Avalon-MM master interface,
exactly as shown for the two custom instructions together in Table~\ref{tab:opcodes} and
Figure~\ref{fig:qsys-system}.

\section{Software Design}

\texttt{count\_binary.c} drives the LED pulsing effect entirely in software: an unsigned
\texttt{level} variable is ramped from \texttt{PWM\_LEVEL\_MIN} (0) up to \texttt{PWM\_LEVEL\_MAX}
(10) and back down again, repeating forever, with each step written out through the
\texttt{ALT\_CI\_NCI\_PWM\_CONTROLLER\_0(level, 0)} custom instruction macro generated by Qsys and
a fixed delay between steps. This gives the simple, human-readable 0-10 brightness scale that
\texttt{ci\_pwm\_controller} was designed to accept, rather than requiring the application to
compute raw 8-bit duty values itself.

\begin{lstlisting}[language=C]
/******************************************************************************
 *
 * Description
 * *************
 * Pulses the LEDs up and down in brightness using the PWM custom
 * instruction component (ALT_CI_NCI_PWM_CONTROLLER_0). The duty-cycle
 * "level" ramps from PWM_LEVEL_MIN up to PWM_LEVEL_MAX and back down again,
 * repeating forever, which produces a breathing/pulsing LED effect.
 *
 * Requirements
 * **************
 * This program requires a PWM controller custom instruction component
 * named 'PWM_CONTROLLER_0' to be present in the system (see system.h for
 * the generated ALT_CI_NCI_PWM_CONTROLLER_0(A,B) macro).
 *
 *****************************************************************************/

#include "system.h"

#include <stdbool.h>
#include <stdint.h>
#include <unistd.h>

/* Duty-cycle range accepted by the PWM controller. */
#define PWM_LEVEL_MIN 0
#define PWM_LEVEL_MAX 10

/* Delay between duty-cycle steps, in microseconds. */
#define PWM_STEP_DELAY_US 200000

int main()
{
	uint32_t level = PWM_LEVEL_MIN;
	bool increment = true;

	while (true)
	{
		ALT_CI_NCI_PWM_CONTROLLER_0(level, 0);

		if (increment)
		{
			if (level == PWM_LEVEL_MAX)
				increment = false;
			else
				level++;
		}
		else
		{
			if (level == PWM_LEVEL_MIN)
				increment = true;
			else
				level--;
		}

		usleep(PWM_STEP_DELAY_US);
	}

	return 0;
}
\end{lstlisting}

\section{Testing and Results}

With \texttt{PWM\_CLK\_DIV}~=~194 and \texttt{PWM\_RESOLUTION}~=~254, one full PWM period is
$195 \times 255 = 49{,}725$ system clock cycles. At the DE2's 50~MHz system clock, this gives a PWM
switching frequency of approximately
\[
    f_{\text{PWM}} = \frac{50\times10^{6}\text{ Hz}}{49{,}725} \approx 1.01\text{ kHz},
\]
comfortably above the flicker-fusion threshold of the human eye ($\sim$50--60~Hz), so the LED
brightness appears steady at each level rather than visibly flickering. Table~\ref{tab:level-duty}

off~$\rightarrow$~on~$\rightarrow$~off breathing cycle of $2 \times 10 \times 0.2\text{ s} = 4$
seconds, repeating indefinitely.

\chapter{Conclusions}

This assignment met all three learning outcomes it targeted: an ASM-based design method was used
for both the PWM controller (Figure~\ref{fig:asm-diagram}) and the \texttt{ci\_pwm\_controller}
custom instruction (Figure~\ref{fig:ci-pwm-asm}) (LO1); every hardware block --
\texttt{count\_leading\_ones}, \texttt{pwm}, and \texttt{ci\_pwm\_controller} -- was implemented in
synthesisable Verilog (LO2); and all of it was integrated into a working Nios~II SOPC system in
Quartus/Qsys, synthesised for and run on the DE2's Cyclone~II FPGA (LO4).

\section{What Worked}

Part~A's dual-memory verification strategy -- swapping the Nios~II Processor's reset/exception
vector memory between SRAM and SDRAM so the running test program never overlapped the region under
test -- worked cleanly and both memories passed all sub-tests (data bus, address bus, byte/half-word
access, and per-bit) over their full ranges. Part~B's custom instruction produced a correct,
constant-time leading-ones count and measured an $\sim\!8\times$ speed-up over the equivalent C
routine, with both implementations agreeing on every result checked. Part~C's PWM system produced
the required smooth, repeating off--on--off breathing effect on LEDR10, confirmed on real hardware
in the demonstration video, at a PWM switching frequency well clear of visible flicker.

\section{What Didn't Work Initially}

A few issues came up during development and were resolved before final testing. The memory test's
destructive nature meant the first attempt at testing SDRAM corrupted the running program, since
the executable itself was still linked into SDRAM; this was fixed by moving the reset/exception
vector (and hence the BSP's default section placement) to the other memory for each test
(Figures~\ref{fig:cpu-reset-sram} and~\ref{fig:cpu-reset-sdram}). The standalone PWM ASM design
carried over from the previous assignment also needed rework before it could be used here: its
ports were renamed and its write path re-timed to be recognised as a proper Avalon-MM slave by
Qsys Component Editor, rather than remaining a free-standing block wired up by hand. Finally, an
early version of \texttt{count\_binary.c} checked \texttt{level} against its minimum/maximum
bounds to flip the ramp direction but never actually incremented or decremented \texttt{level}
itself, so the custom instruction was always called with \texttt{level~=~0} and no pulsing
occurred; this was caught during testing and fixed.

\section{Critical Assessment}

\textbf{Part~A.} Strengths: the design cleanly separates SRAM and SDRAM testing by relocating only
the CPU's reset/exception vector, and both memories are verified over their full advertised
capacity. Weakness: this approach requires two separate BSP rebuilds and re-programming cycles
rather than a single run that exercises both memories simultaneously under load.

\textbf{Part~B.} Strengths: the combinational priority-encoder implementation gives constant,
data-independent single-cycle latency and a measured $\sim\!8\times$ speed-up over software, using
a small, well-structured circuit. Weakness: it consumes FPGA logic resources and one of a limited
number of custom instruction opcode slots, and -- unlike the software routine -- is tied to this
specific Nios~II system rather than being portable to another target without hardware changes.

\textbf{Part~C.} Strengths: splitting the design into a reusable, general-purpose \texttt{pwm}
Avalon-MM peripheral and a separate \texttt{ci\_pwm\_controller} custom instruction keeps the duty
generation logic reusable while giving application code a simple 0--9 brightness scale instead of
raw duty values. Weaknesses: the level-to-duty mapping in Table~\ref{tab:level-duty} is linear,
whereas human brightness perception is closer to logarithmic, so the perceived brightness steps are
uneven (they appear to change faster at the low end than the high end); and levels 9 and 10 both
saturate to the same maximum duty value, making them visually indistinguishable.

\section{How the System Was Fully Tested}

Part~A was tested using the Nios~II IDE's Memory Test utility in both directions, exercising the
complete 512~KB SRAM and 8~MB SDRAM address ranges (Table~\ref{tab:mem-regions}) and all of its
built-in sub-tests. Part~B was tested with a 100{,}000-iteration timed benchmark that ran the
identical pseudo-varied input pattern through both the software routine and the hardware custom
instruction, so their results and timings could be compared directly on equal terms
(Table~\ref{tab:sw-vs-hw}). Part~C was tested by observing the physical LEDR10 output on the DE2
board over multiple full breathing cycles, recorded in the linked demonstration video, confirming
the LED reaches both its off and fully-on extremes and transitions smoothly between them as
required.
